# PAYPHONE: IPv4 VPN на Rust, QUIC и одном очень вредном Mac

Собрал экспериментальный VPN с нуля: TUN внутри QUIC+TLS 1.3, подписка на Ed25519, обфускация UDP «как у Hysteria», optional REALITY на TCP 443, full-tunnel на macOS/Linux/Windows. Не продукт и не «замена WireGuard». Инженерный прототип, который уже гоняет браузер через VPS на 443/udp — и по дороге несколько раз очень убедительно ломался.

Репозиторий: [github.com/digkill/PAYPHONE](https://github.com/digkill/PAYPHONE). Сейчас это **v0.2.0**.

## Зачем ещё один VPN

WireGuard отличный. Мне хотелось другого: понять стек целиком и сделать транспорт, который **не выглядит как QUIC** на проводе.

QUIC узнаваем даже на «нестандартном» порту: long header, version, характерный handshake. DPI не обязан расшифровать трафик — достаточно пассивно сматчить сигнатуру или **самим постучаться** на IP:port, завершить handshake и занести сервер в блоклист. Типичный ответ «просто повешу Quinn на 443» эту историю не закрывает: байты всё равно QUIC.

Поэтому PAYPHONE — это не «HTTP/3 прокси», а **IP-пакеты из TUN**, упакованные в QUIC datagrams, плюс тонкий XOR-слой с общим секретом, чтобы слепой probe не получал даже QUIC-ответа.

Это не маскировка под чужой сайт — *пока речь про UDP*. На TCP 443 есть опциональный REALITY (ниже): probe без ключа уезжает на настоящий сайт, свой клиент проходит Xray-совместимый `session_id`. Внутри всё равно кадры PAYPHONE, не VLESS.

## Как устроено

Семь крейтов в одном workspace:

| Крейт | Зачем |
| --- | --- |
| `payphone-core` | Кадры, кодеки, константы |
| `payphone-auth` / `payphone-token` | Подписка: Ed25519, claims, CLI выпуска токенов |
| `payphone-transport` | Quinn, TLS, обфускация UDP, REALITY на TCP |
| `payphone-tun` | utun/`payphone0`/Wintun, маршруты, NAT |
| `payphone-server` / `payphone-client` | Сессии, handshake, пересылка |

Внутри VPN плоская сеть `10.77.0.0/24`. Сервер всегда `10.77.0.1`, клиенты с `.2`. Снаружи контейнер слушает свой `40404`, хост публикует **443/udp** — тот же порт, что у настоящего HTTP/3. Это не камуфляж трафика, только менее глупый номер порта, чем `40404`.

Полный туннель: на сервере forwarding + MASQUERADE, на клиенте два маршрута `/1` (`0.0.0.0/1` и `128.0.0.0/1`) через `10.77.0.1`. Классика: default не трогаем, а более специфичные `/1` перехватывают весь IPv4.

## Протокол, который разговаривает как человек

Каждый кадр — 16 байт заголовка и payload. Типы такие:

- `WhatsUpDude` — клиент приходит с токеном
- `AllGoodDude` — сервер выдаёт адрес и resume-секрет
- `BackAgainDude` / `StillGoodDude` — переподключение без нового токена
- `AccessDeniedDude` — токен протух, отозван, неизвестный ключ
- `Data` — настоящий IPv4-пакет
- `Ping` / `Pong` — keepalive с джиттером, не метроном на 10.000 с

Имена нарочно дурацкие. Бинарный формат — нет: version, type, flags, length, sequence, сеть в big-endian, жёсткие лимиты длины.

Сессии живут на диске, отзывы токенов — в файле `token_id` по строке (`payphone-token revoke`), сервер перечитывает по mtime. План, лимит устройств и Mbps в токене теперь энфорсятся. Клиент пинит self-signed сертификат файлом `dev-certs/payphone-cert.der`. Для прототипа ок. Если есть DNS-имя — `PAYPHONE_TLS_DOMAIN` и Let's Encrypt на том же 443 (TLS-ALPN-01); клиент с `--server имя:443` сам берёт публичные CA. На REALITY-пути пин не нужен: HMAC-лист проверяется как у Xray.

## Почему datagrams, а не стримы

VPN возит IP. IP уже умеет терять пакеты. Если засунуть его в надёжный QUIC stream, получится TCP-over-TCP: внутренняя потеря плюс внешний ретрансмит, head-of-line, боль.

Поэтому payload едет **unreliable datagram**. Потерял — пусть внутренний TCP/QUIC сам решает. Quinn при переполнении буфера выкидывает старые datagrams; для туннеля это правильнее, чем ждать окно и стопорить TUN.

Первая версия ждала каждый `send_datagram_wait`. Под нагрузкой исходящий пакет блокировал входящий: select-цикл не крутился, пока Quinn не запишет. Лечится одной сменой на `send_datagram` и дропом при `TooLarge`.

## Обфускация: не шифр, а «заткнись, probe»

Поверх уже зашифрованного QUIC:

```text
[ 8 байт salt ][ XOR( SHA256(psk || salt) по кругу,
                      [u16 длина][payload][случайный хвост 0–32] ) ]
```

Без секрета пакет слишком короткий или с враньём в length — сокет **молчит**, Quinn его не видит. Слепой handshake снаружи не начинается.

Это не криптография. Конфиденциальность уже у TLS 1.3. Слой только ломает сигнатуру и активный пробинг.

Что он **не** прячет: один долгоживущий UDP 4-tuple, кластеризацию размеров, факт «сервер отвечает не всем». Чтобы притвориться чужим сайтом на 443/tcp, нужен другой транспорт — и он есть, default **off**.

## REALITY на TCP, не VLESS внутри

Включаешь `PAYPHONE_REALITY=on`, dest вроде `www.microsoft.com:443`, X25519 + shortId. Проба без auth уезжает на dest целиком. Свой клиент: Chrome 131-shaped ClientHello (GREASE по краям как в uTLS `ShuffleChromeTLSExtensions`, в середине shuffle, GREASE ECH, настоящий ML-KEM-768 public + X25519). Побитово как живой Chrome — нет: GREASE/ECH/KEM каждый раз случайные, и Chrome сам едет каждый месяц. Гнаться за дампом бессмысленно.

Дальше как у Xray: ServerHello dest с патчем только X25519 `key_share` (JA3S dest), размеры зашифрованного хвоста и post-handshake `0x17` — три ALPN-пробы dest (none / http/1.1 / h2), берём класс из ClientHello. Содержимое EncryptedExtensions снаружи не видно: это AEAD. Мы эхоим клиентский ALPN; копировать plaintext dest нельзя, ключей handshake dest у нас нет.

VLESS/Vision не делал и не буду, пока сам не попрошу: внутренний протокол — PAYPHONE. Xray-клиент с теми же ключами пройдёт наружу и упрётся в чужие кадры. Coolify REALITY не включал: без dest+ключей на 443 должна остаться лендинг-страница.

### Баки, которые убили MTU

Первая версия паддинга округляла длину до корзины вроде `[128, 296, 568, 1200, 1440]`. Звучит умно против DPI.

Проблема: через этот слой проходят **все** UDP Quinn, включая пробы PMTU. Пакет у потолка 1200 прыгал сразу в 1440, проба не возвращалась, Quinn занижал оценку — и честный кадр приложения ловил `SendDatagramError::TooLarge`.

Сейчас хвост маленький и равномерный, 0–32 байта. Корзины выкинул.

## Три раза, когда «протокол медленный», а виноват не протокол

### 1. MTU 1280 «потому что IPv6»

RFC говорит: 1280 безопасно. QUIC гарантирует другое: UDP payload 1200 до discovery. У Quinn накладные расходы, у PAYPHONE ещё 40 байт (16 кадр + 24 DATA). Итог: 1280 IP не влезает в безопасный datagram.

На реальном деплое клиент падал на первом же «толстом» браузерном пакете. Сейчас TUN **1100**: 1100+40=1140 внутри пола ~1154. Браузеру хватает. Гигабита на этом не будет, пока не поднимем MTU после нормального path-MTU.

### 2. macOS убивает маршрут к серверу

Туннель вставал: handshake, `10.77.0.x`, тысячи пакетов. Потом QUIC внезапно умирал. На 2ip снова домашний адрес.

`networksetup` (выключить IPv6 / прописать DNS) **пересобирает таблицу маршрутов**. Host-route к VPS исчезал, `128.0.0.0/1` заглатывал IP сервера, QUIC уходил в свой же utun — петля — сессия мертва.

Вторая ловушка: маршрут `-ifscope en0` виден только scoped lookup. Quinn смотрит unscoped и всё равно попадает в `/1`. Нужен обычный `/32` через LAN-шлюз.

Третья: watchdog был `sleep(2)` **внутри** `select`. Каждый пакет с TUN пересоздавал таймер, под трафиком обход **никогда** не чинился.

Сейчас:

- `networksetup` не трогаем: IPv6 режется `route -blackhole`, DNS — через `scutil`;
- unscoped `/32` на сервер + `IP_BOUND_IF` на UDP, чтобы пакеты физически уходили в Wi-Fi;
- отдельный `interval` 400 мс, который чинит и `/32`, и оба `/1`.

### 3. Ctrl+C и мёртвый интернет

Tokio перехватывает SIGINT. Первый Ctrl+C выходил из цикла и зависал в `endpoint.wait_idle()`, пока `/1` ещё смотрели в utun. Второй Ctrl+C уже никто не слушал. Интернет «отваливался», клиент «не выключался».

Маршруты нужно снимать **до** ожидания QUIC, а `wait_idle` ограничить таймаутом. После стопа должен остаться LAN default, не чёрная дыра.

## Клиент, который выглядит как Matrix

Это не помогает протоколу. Это помогает не ненавидеть `sudo ./payphone-client`. Перед коннектом — digital rain на весь терминал, в центре «Follow the white rabbit.». Пока туннель открыт, те же столбцы живые: пакеты сгущают дождь, сверху счётчик.

Катакана только полуширинная. Полноширинная в Terminal.app занимает две колонки, `\r` считает одну — и в «матрицу» вклеиваются `17291` и `pkts^C`. Обидно и глупо, лечится шириной глифа.

## Что сознательно не сделано

- Только IPv4 в туннеле. IPv6 с клиента глушится blackhole `::/1` + `8000::/1` на macOS, Linux и Windows, иначе браузер уезжает на AAAA провайдера.
- Нет своего DNS-резолвера (есть stub `10.77.0.1:53`). GSO/GRO на Linux включён в `ObfuscatedSocket`.
- REALITY в Coolify не включён по умолчанию. С `PAYPHONE_TLS_DOMAIN` своё имя оставляет лендинг, остальное splice на dest. VLESS/Vision нет и не планируется, пока не попрошу отдельно.
- ClientHello как uTLS Chrome 131, не дамп живого Chrome. EncryptedExtensions plaintext dest не копируем — он внутри AEAD.

Для прототипа v0.2.0 этого хватает: коннект живой, 2ip показывает адрес VPS, Ctrl+C возвращает интернет.

## Если повторять

1. Не верьте MTU «как в RFC для IP», пока не посчитаете бюджет **конкретного** datagram API.
2. Любая обфускация размера обязана пропускать PMTU-пробы без скачков.
3. На macOS `networksetup` — ядерное оружие против вашей же routing table.
4. Scoped route ≠ route, который видит ваш сокет.
5. Не сериализуйте TUN за `send_datagram_wait`.
6. SIGINT, который «выключает VPN», должен сначала вернуть default, и только потом вежливо прощаться с QUIC.

Дальше по плану — dual-stack и включать REALITY в Coolify только когда dest, ключи и (лучше) своё DNS-имя лежат рядом с деплоем. Let's Encrypt: `PAYPHONE_TLS_DOMAIN`. Если будет вторая статья, она скорее всего снова про маршруты, а не про кадры.
